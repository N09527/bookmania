## 範圍

你在 11/28 的要求：

> 1.原本yokai有的擴充來源功能，iOS應該也能透過App內進行擴充，有個叫Tachimanga的APP有做到
> 2.能夠透過webdav做到同步書櫃及即時同步進度（開始閱讀及離開閱讀時同步），讓不同裝置或平台都可以接續閱讀狀況

重述版本：

1. iOS 版也要有 Android 版（沿用自 Yōkai）的擴充來源功能：在 App 裡加入來源庫、安裝擴充、用擴充瀏覽與閱讀線上的作品。
2. 用 WebDAV 同步書櫃與閱讀進度：開始閱讀時取得最新進度，離開閱讀時送出進度。Android 與 iOS 之間、同平台的不同裝置之間，都能接著讀。

這兩項原本在「不要自行加入」的清單裡（線上書庫、雲端同步），現在是你提出的，所以列入範圍。其他約束不變：DRM、書籍內容的隔離、授權、相容性、不送出當機報告或分析資料。

## 1. 查證結果

### 1.1 Tachimanga【二手】

Tachimanga 的網站與 App Store 頁面，在這個環境無法連線（網域解析失敗）。以下都只來自搜尋結果的摘要：

- iOS／iPadOS 的漫畫閱讀 App，可以使用 Tachiyomi 系的擴充。
- 它安裝的擴充是 `.jar` 檔，Mihon 用的是 `.apk`。社群有人專門為它發布 .jar 版的來源庫，也有人回報某些經過 R8 最佳化的擴充會在它上面出現 `java.lang.VerifyError`。
- 有備份與還原，可以匯入 Tachiyomi 的備份，備份檔可以放在 iCloud Drive。
- 發行者是 Tekbrio LLC，沒有找到它的原始碼。
- 它在 iOS 上**用什麼方式**執行擴充，沒有找到官方說明。

### 1.2 Oneechan runtime【已查證：讀過它的 README、NOTICE、jvm-ios/README，提交 `4a414a0`，2026-10-28】

這是另一個 iOS 漫畫 App「Oneechan」的擴充執行環境，原始碼公開在 [leros1337/oneechan-runtime](https://github.com/leros1337/oneechan-runtime)。

**做法**

- 在 iPhone 上直接執行**未修改的** Tachiyomi／Mihon 擴充，APK 或 .jar 都可以，不需要伺服器。
- App 裡靜態連結一個 Java 虛擬機（Eclipse OpenJ9 0.61.0），只用直譯模式，因為 iOS 不允許 JIT。
- 擴充的 dex 在裝置上用 dex2jar 轉成 jar 再載入。
- 虛擬機上跑一個 Kotlin 寫的「擴充主機」，它建立在 Suwayomi 的 Android 相容層與 Tachiyomi 的來源 API 上。
- App 與主機之間用 JSON-RPC 溝通，在裝置上經由 JNI。
- **由 App 提供的部分**：擴充的網路請求可以交給 App 的 URLSession；Cloudflare 驗證在 WKWebView 裡完成；需要 Android WebView 的擴充改用 WKWebView；QuickJS 介面改跑在 JavaScriptCore。

**功能與信任**

- 來源庫支援 `index.min.json` 與 `index.pb`。
- 安裝時會檢查擴充的程式庫版本與簽章；不認得的簽署者要使用者同意信任，與 Mihon 相同。
- 擴充可以做的事：熱門、最新、含篩選的搜尋、作品資訊、章節、頁面、圖片、相關作品、來源設定。

**授權**：它自己的程式碼是 MPL-2.0。內含或建置時使用的元件：

| 元件 | 授權 |
|---|---|
| Suwayomi-Server（git 子模組） | MPL-2.0 |
| Android API 簽名 | Apache-2.0 |
| dex2jar | Apache-2.0 |
| OpenJ9 與 OMR | 採 Apache-2.0 |
| OpenJDK 21 類別庫與原生程式庫 | **GPL-2.0 加 Classpath Exception** |

它的 NOTICE 也附上了提供原始碼的書面承諾。

**大小與效能**：2026-10-22 在 M4 Pro 的模擬器上量測：

| 項目 | 數值 |
|---|---|
| Release 版 App 大小 | 198.6 MB（虛擬機的 Java 執行環境 92 MB、擴充主機 71 MB、執行檔 23.6 MB） |
| 擴充主機就緒 | 0.533 秒 |
| App 開機後的記憶體 | 322 MB |
| 測試流程中的記憶體峰值 | 660 MB |

**建置**：第一次完整建置在 M4 Pro 上約 40 分鐘。它使用 Xcode 27.1，最低 iOS 26.0。

**它自己寫的限制**：「Not yet run on a physical device」，也就是作者寫這份說明時還沒在實機上跑過；裝置版能編譯與連結。

**缺的部分**：App 端的程式（Swift 的 JNI 接口、RPC 用戶端）在 Oneechan App 的存放庫裡。那個存放庫在這裡無法匿名讀取（git 要求帳號），【推論】它不是公開的，所以這部分要自己寫。

## 2. iOS 的擴充來源

### 2.1 做法的選項

| | A. App 內建虛擬機（Oneechan runtime 的做法） | B. 連到自架的 Suwayomi-Server | C. 不做 |
|---|---|---|---|
| 擴充在哪裡執行 | iPhone／iPad 上 | 你的電腦或 NAS 上 | — |
| 是否符合「App 內進行擴充」 | 是 | 擴充在伺服器上管理，App 只是用戶端 | — |
| App 大小 | 約 200 MB（依 1.2 的量測）；目前的 IPA 約 1 MB | 幾乎不變 | 不變 |
| 需要伺服器 | 不需要 | 要一直開著 | — |
| 授權義務 | 要提供 OpenJDK 類別庫等元件的原始碼（GPL-2.0），以及 MPL-2.0 檔案的原始碼 | 伺服器另外安裝，App 不含它 | — |
| 主要風險 | 執行環境還沒有實機紀錄；建置很重；直譯模式較慢、記憶體較多 | 要維持伺服器與連線 | — |

【建議】A，因為只有它符合你說的「透過 App 內進行擴充」。B 列出來，是給你比較用的。

### 2.2 如果選 A，要做的事

1. **執行環境**：
   - 以 Oneechan runtime 的固定版本為子模組。
   - 在 GitHub 的 macOS 執行器上建置 iOS 版虛擬機，結果存進快取，只有版本改變時才重建。
   - 它的建置用 Xcode 27.1，我們目前的建置用 Xcode 26.6【已查證：1.2.0 的 IPA 記錄的是 Xcode 26.6】。GitHub 上能不能取得對應的 Xcode，或要不要改它的修補檔，要實際試過才知道。
2. **App 端的接口**（Swift）：啟動虛擬機與主機、JSON-RPC 用戶端、擴充網路請求改走 URLSession、Cloudflare 用的 WKWebView、JavaScriptCore。它的 `contract/fixtures` 有每個請求與回應的範例 JSON，可以拿來寫測試。
3. **介面**：
   - 來源庫與擴充的管理：加入來源庫、安裝、更新、移除、信任簽署者。
   - 來源清單、瀏覽（熱門、最新）、搜尋與篩選、來源設定。
   - 線上作品頁、章節清單、線上的圖片閱讀。
4. **書櫃整合**：
   - 書櫃、分類、閱讀記錄、備份目前只認得本機作品，要擴大到線上作品（以來源 id 與網址識別，同 Android）。
   - 備份也要能還原線上來源的作品；1.2.0 目前會略過它們。
5. **不內建任何來源庫**：與 Android 版相同，來源庫網址由你自己加入。
6. **安全**：
   - 擴充是第三方程式碼，在 App 裡執行時可以連網，也可以讀寫 App 自己的檔案。
   - 這與 Android 上的情形相同：擴充在 App 的程序裡執行。
   - 帳號密碼（例如第 3 節的 WebDAV）存在 iOS 的鑰匙圈，擴充程式碼碰不到【推論：Java 程式碼只能使用虛擬機提供的檔案與網路功能】。
   - 書籍內容的隔離不受影響：電子書閱讀器的 WKWebView 規則維持不變。
7. **驗證**：
   - 在這裡：擴充主機在 Linux 上跑單元測試。
   - 在 GitHub 的 iOS 模擬器上：用我自己寫的測試擴充跑介面測試，它只回傳固定的測試資料，不連任何真實網站。
   - 實機：只能由你在裝置上確認。

【推論】這是比 iOS-2～6 加總更大的工作，至少要分 4～5 個階段（執行環境、接口、擴充管理、瀏覽與閱讀、書櫃與備份整合）。

## 3. WebDAV 同步（Android 與 iOS）

### 3.1 同步什麼【建議】

- 書櫃：哪些作品在書櫃、分類與作品所屬的分類。
- 每個書檔（章節）：已讀、書籤、頁數、文字書的閱讀位置。
- 閱讀記錄：最後閱讀時間、閱讀時間。
- 不同步：書檔本身、設定、匯入的字型（你沒有提到；要的話見第 5 節第 3 題）。

### 3.2 遠端的結構【建議】

- 伺服器上一個資料夾，例如 `Bookmania/sync/v1/`。
- 每台裝置只寫自己的檔案：`devices/<裝置 id>/library.json`，以及每部作品一個 `progress/<作品代碼>.json`。
- 合併規則：讀取時合併所有裝置的檔案，每一筆資料以修改時間較新的為準。
- 這樣兩台裝置不會同時改到同一個檔案，不需要伺服器支援鎖定或條件寫入。WebDAV 伺服器之間的差異很大，這樣做比較穩【推論】。
- 已知限制：以各裝置的時鐘判斷新舊，時鐘差很多時可能判斷錯【推論】。

### 3.3 什麼時候同步【建議】

- **開始閱讀時**：先取得這部作品在其他裝置的最新進度，最多等幾秒，再開到最新的位置；連不上時用本機的進度。
- **離開閱讀時**：送出這部作品的進度。手機上切到別的 App 也算離開，送出時向系統要求短暫的背景時間。
- **書櫃**：App 開啟或回到前景時同步；書櫃有變更時，等一下再一起送出。
- **離線時**：記下待送的變更，下次連上時送出。

### 3.4 作品怎麼對應

- 本機來源：以「作品資料夾名稱／書檔名稱」對應，兩個平台的規則相同，就像現在的備份互通。所以兩台裝置要用相同的資料夾名稱與檔名。
- 線上來源（有擴充之後）：以來源 id 加作品網址對應，同 Android 的備份。

### 3.5 帳號與連線【建議】

- 伺服器網址、帳號、密碼在兩個平台的設定裡輸入。密碼存在 iOS 的鑰匙圈，Android 則用系統金鑰庫加密保存。
- 預設只允許 HTTPS。如果你的伺服器在家裡的區網、只有 HTTP，要另外開啟，並顯示提醒；iOS 也會詢問是否允許存取區域網路。
- 同步資料只送到你設定的伺服器，不送到其他地方。

### 3.6 驗證方式

- 在這裡執行一個測試用的 WebDAV 伺服器（例如 Python 的 WsgiDAV，只用於測試，不包進 App）：
  - Kotlin 與 Swift 的同步程式各自對它測試；
  - 再測交叉的情況：Android 寫、iOS 讀，以及反過來。
- Android：在模擬器上實際操作。
- iOS：單元測試與 GitHub 上的編譯；介面要你在實機上確認。

【推論】分 3 個階段：同步核心與測試、Android、iOS。

## 4. 建議的順序【建議】

1. 先做 WebDAV 同步：範圍明確，兩個平台都用得到，也能在這裡完整測試核心。
2. 再做 iOS 的擴充來源：先用一個階段，在 GitHub 上把執行環境建出來並裝進 App。這一步成功，才繼續做介面。
